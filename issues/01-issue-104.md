## What to build

Establish the trust-boundary sanitiser as a deep, pure module with a stable surface (`safeHeaderValue`, `safeChannelName`, `safeRouteSegment`, `safeStructuredKey`) and prove it end-to-end by applying it to its first sink: the HTTP forward proxy's outbound headers. The sanitiser rejects on attacker-shape inputs by default; strip mode is opt-in per call site.

This slice ships the foundation everything else builds on. After it lands, a malicious client whose request flows through `http-forward` (non-MITM mode) cannot smuggle CRLF, NUL, or control characters into upstream headers — the upstream observes a sanitised header set or the proxy returns the documented rejection.

## Acceptance criteria

- [ ] A new sanitiser module exposes `safeHeaderValue`, `safeChannelName`, `safeRouteSegment`, `safeStructuredKey` with documented per-sink rules (length limit, accepted character classes, normalisation, reject vs strip behaviour).
- [ ] The sanitiser has zero I/O, zero filesystem, and zero protocol coupling — pure function inputs to outputs / tagged errors.
- [ ] Table-driven unit tests cover CRLF, NUL, control characters, oversized inputs, malformed UTF-8, Unicode confusables, and header continuation tricks across all four sinks.
- [ ] HTTP forward proxy applies `safeHeaderValue` to every header it copies into the upstream request, in addition to the existing hop-by-hop stripping.
- [ ] Integration test boots the forward proxy, fires a client request whose header value contains `\r\n`, observes the upstream connection, and asserts the upstream sees a sanitised header set (no injected headers).
- [ ] Integration test asserts the documented error response when a request fails sanitisation in reject mode.
- [ ] The sanitiser is exported from a stable public path so application code can reuse it.
- [ ] No regression for the existing `test/proxy/` suite.
