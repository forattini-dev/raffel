## What to build

Apply `safeHeaderValue` to the CONNECT MITM intercept path of `connect-tunnel`. The MITM mode decrypts HTTPS, exposes `onRequest` / `onResponse` hooks, and re-emits the request to the upstream. Today the existing hop-by-hop strip runs but no sanitiser does — a malicious client (or a buggy user hook) can land CRLF-injected headers either at the upstream or at the downstream client. This slice closes both directions.

End-to-end behaviour: with a CONNECT tunnel in MITM intercept mode, malicious request headers reaching the upstream and malicious response headers returning to the client are both sanitised. The existing `onRequest` / `onResponse` hook signatures do not change; the sanitiser runs around them so user-supplied modifications also pass through it before hitting the wire.

## Acceptance criteria

- [ ] CONNECT MITM intercept applies `safeHeaderValue` to every header copied into the upstream `https.request` call.
- [ ] CONNECT MITM intercept applies `safeHeaderValue` to every header written back on the downstream client response.
- [ ] Existing `onRequest` / `onResponse` hook signatures and behaviours are preserved. User modifications observed by the wire pass through the sanitiser.
- [ ] Integration test boots a MITM tunnel, fires a client request with CRLF in a header value, asserts the upstream observes a sanitised header set.
- [ ] Integration test boots a MITM tunnel against a malicious upstream that responds with CRLF in a header value, asserts the downstream client observes a sanitised response header set.
- [ ] Integration test exercises a user hook that injects a header containing CRLF; asserts the wire receives a sanitised version.
- [ ] No regression for the existing CONNECT tunnel + MITM tests in `test/proxy/`.
