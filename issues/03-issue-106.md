## What to build

Apply `safeChannelName` at the WebSocket subscribe and publish entry points. Today a client-supplied channel name flows into the channel registry, the policy engine action, the metrics surface, and structured logs without character-class validation — a malicious client can plant CRLF, NUL, or `;` into any of those sinks. This slice rejects malformed channel names at ingress before any of those side effects fire.

End-to-end behaviour: a WebSocket client that issues a `subscribe` or `publish` with a non-conforming channel name has the connection closed with WebSocket close code 1008 (Policy Violation). The registry, policy engine, and metrics counter never observe the malformed name. A configurable allowlist (regex + max length) lets users tighten beyond the safe defaults.

## Acceptance criteria

- [ ] WebSocket subscribe handler runs `safeChannelName` on the client-supplied channel name before any registry lookup or policy evaluation.
- [ ] WebSocket publish handler does the same.
- [ ] Failed validation closes the connection with code 1008 and a documented reason.
- [ ] Default allowlist + max length are documented and conservative.
- [ ] Channel options surface accepts a stricter regex / max length override.
- [ ] Integration test subscribes with a channel name containing CRLF, NUL, and `;`; asserts the close code, asserts no entry appears in the registry, asserts the policy engine is not invoked.
- [ ] Integration test publishes with a malformed channel name; asserts the same outcome.
- [ ] No regression for the existing `test/adapters/websocket.int.test.ts` and `test/policy/co-located/channel.int.test.ts`.
