## What to build

Close the remaining ingress sinks identified in the audit by applying `safeStructuredKey` (or `safeRouteSegment`, whichever fits) at three concrete entry points:

1. **JSON-RPC method dispatch** — the dispatched method name is validated before registry lookup or logging.
2. **MCP tool / resource ingest** — incoming tool names and resource URIs are validated before flowing into the MCP message stream or downstream handler.
3. **HTTP → procedure-metadata copy paths** — anywhere a request header or path segment is copied into procedure metadata, structured logs, or downstream protocol metadata, the copy passes through the sanitiser.

End-to-end behaviour: malicious clients on any of the three protocols cannot land CRLF, NUL, or delimiter characters into the registry, the logs, or downstream metadata. Each sink rejects with the documented error code for that protocol.

## Acceptance criteria

- [ ] JSON-RPC dispatch path validates the incoming `method` string with the sanitiser; rejection produces the documented JSON-RPC error response.
- [ ] MCP message ingestion validates tool names and resource URIs; rejection produces the documented MCP error.
- [ ] Every HTTP-to-procedure-metadata copy path (request path segments, copied request headers) goes through the sanitiser; behaviour on rejection is documented per sink.
- [ ] Integration test per protocol: malicious request with CRLF / NUL in the relevant identifier; asserts the documented rejection and the absence of side effects (registry, log, metric).
- [ ] No regression for the existing JSON-RPC, MCP, or HTTP suites.
